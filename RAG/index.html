RAG : 


Retrieval Augmented Generation (RAG) is a method that helps a Large Language Model (LLM) give better and more accurate answers by allowing it to look up information from external data sources before answering.


How is RAG different from fine-tuning an LLM?

Fine-tuning means: You retrain the model on new data so it “learns” that information permanently. Fine-tuning means changing the model itself by training it on new examples.


RAG means: You do not retrain the mode : it means keeping the model the same, but giving it extra information at runtime.

You simply give it relevant information at the time of answering.


Fine-tuning:

  • Expensive
  • Time-consuming
  • Requires retraining
  • Hard to update frequently
  • Information becomes part of the model

RAG:

  • Faster to implement
  • Easier to update (just update the database)
  • No retraining required
  • More flexible
  • Information stays outside the model


RAG focuses on knowledge access, while fine-tuning focuses on behavior and style.


If the problem is about knowledge access → use RAG

If the problem is about behavior change → use fine-tuning


You should prefer RAG when:


• Your data changes frequently

• You need up-to-date information

• You are using private or company documents

• You want lower cost and faster implementation

• You need traceable answers (with sources)


For example:

  • Customer support chatbot using internal knowledge base
  • Legal document assistant
  • Company HR policy bot
  • Medical research assistant

In all these cases, data updates often. Retraining every time would be expensive and slow.


Fine-tuning is better when:

  • You want to change writing style or tone
  • You want domain-specific language behavior
  • You want the model to follow a strict format
  • You want behavior improvement, not just knowledge access



Why RAG Exists: The Problems with a Plain LLM :

Knowledge Cutoff

Hallucination : Generating fluent, plausible content that is unsupported or false.


RAG over a vector index is right for slowly to moderately changing unstructured knowledge. For real-time state, the "retrieval" step should be an API call


CITATION : You cannot cite weights. Banking, healthcare, legal, and insurance all require traceability: "show me where it says that." RAG provides source IDs, page numbers, sections, and versions.

No Access Control in Weights - A model cannot know that user A may see the M&A folder and user B may not. Anything in the weights is available to anyone who can prompt the model. RAG enforces authorization at retrieval time, so the LLM only ever sees documents the requesting user is allowed to see.


Context Injection and Grounded Generation

Context injection means placing retrieved text into the prompt so it becomes part of the conditioning sequence. 

Grounding is the property that every factual claim in the output is supported by the provided evidence. Injection is the mechanism; grounding is the contract. Injection alone does not guarantee grounding, because the model can still ignore, misread, or supplement the context.

It has Evidence (Relevant), Instruction ("Answer only from sources; say if not found"), Attribution (Cite source IDs per claim),Abstention (n explicit, acceptable "I don't know" path), Verification (Post-generation check: claims ⊆ evidence)

RAG : 

"RAG, Retrieval-Augmented Generation, is a pattern where at inference time we retrieve evidence relevant to the user's question from an external knowledge store and inject it into the LLM's context, so the answer is grounded in, and attributable to, that evidence.

It exists because an LLM has two kinds of memory. Its weights are frozen at a training cutoff, lossy for long-tail facts, contain none of our private data, and can't enforce permissions. Its context window is precise but only lasts for one request. Models are much better at reading than remembering, so RAG's job is to find the right text and put it in front of the model.

That addresses four enterprise problems. Freshness: updating knowledge means re-indexing a document, not retraining. Private data: our documents stay in our store. Attribution: every claim can cite a source. And the one people often miss, access control: we filter by the user's permissions at retrieval time, so the model only ever sees what that user is allowed to see.


"What's the difference between faithfulness and correctness?"

Faithfulness compares the answer with the context; correctness compares it with the truth. A faithful answer built on an outdated source is still wrong.


1 . Metadata : 

Chunking creates the searchable units; metadata tells the retrieval system what those units are, where they came from, who can access them, and when they are valid.

metadata is one of the things that makes retrieval accurate, secure, filterable, and maintainable.

1.1 : Metadata Enrichment : Make every chunk filterable, rankable, citable, and securable:

Source metadata : doc_id, title, URL, author, created_at / modified_at, source system:

Structural metadata : heading_path ("Policy > Refunds > 7.2 Disruption"), page, chunk_index, parent_id

Security metadata : tenant_id, acl_groups, classification, data residency region

Lifecycle metadata : version, effective_from / effective_to, status (active / superseded / deleted)

Semantic metadata : language, doc_type, product, region, entities, keywords, summary, hypothetical questions

Common problems : Inconsistent tags (UAE vs AE vs United Arab Emirates) causing silent filter misses; hallucinated LLM metadata; stale ACLs


Don't think of metadata as "extra information attached to a chunk." Think of it as the control plane for your RAG system — it enables retrieval filtering, security, freshness, provenance, governance, and operational debugging.



2 . CHUNKING : 



2.1 Core Concepts :


  • size
  • overlap
  • Semantic boundaries.: Natural units of meaning: sentence, paragraph, section, clause, function. Cutting between them preserves meaning; cutting through them destroys it.
  • Context preservation. Each chunk must be interpretable on its own.


2.2 Chunking Strategies : 


  • Fixed-Size + overlap
  • Sentence-Based Chunking
  • Paragraph-Based Chunki ng
  • Recursive Chunking :  
    • How it works. Try the "largest" separator first (\n\n). If a resulting piece is still too big, split that piece with the next separator (\n, then . , then , and finally individual characters). Then greedily merge the small pieces back up to the size limit.
    • Why it works: it prefers the most meaningful boundary available and only falls back to weaker boundaries when forced to.


  • Semantic Chunking : Embed each sentence, measure the similarity between consecutive sentences, and cut where the topic "jumps." The most common approach uses embedding distance thresholds, where you calculate the similarity between consecutive sentences and split the text when that similarity drops below a specific target.

One-line definition for interviews : Semantic chunking is a RAG preprocessing technique that uses semantic similarity between neighboring text segments to identify meaningful topic boundaries, producing coherent chunks that improve the quality of retrieval and downstream LLM responses.


  • Parent-Child Chunking (Small-to-Big) : Parent-Child Chunking is a RAG retrieval strategy where a document is divided into small child chunks for precise retrieval, while each child chunk belongs to a larger parent chunk that contains broader context.

This solves a common RAG problem: small chunks retrieve precisely but may lack context; large chunks provide context but can hurt retrieval precision.

Parent-child chunking separates retrieval granularity from generation context by indexing small child chunks for precise semantic search while using their larger parent chunks to provide sufficient context to the LLM.


Interview scenario

Interviewer:

"You have a 500-page hotel policy document. Some policies are very detailed. How would you chunk it?"

A strong answer:

"I wouldn't immediately choose a fixed token size. First I'd preserve the document hierarchy—document, section, subsection and paragraph. I'd create parent chunks around coherent sections and then divide those parents into smaller child chunks based on semantic or structural boundaries. I'd embed the child chunks because they provide more precise retrieval representations, while maintaining a parent ID for each child. At query time, I'd retrieve the top-K child chunks, expand their parent IDs, deduplicate the parents, and optionally rerank the parent candidates. I'd then construct the final context within a token budget and send that to the LLM. Finally, I'd compare this against recursive or semantic chunking using retrieval and answer-quality metrics."


  • Proposition chunking (the "Dense X Retrieval" line of work) uses an LLM to rewrite text into atomic, self-contained factual statements ("The flight-disruption exception excludes corporate-account bookings."). This gives very high precision, but ingestion is expensive.


2.3 What Goes Wrong: Size and Overlap Failure Modes : 


  • Chunk too small : The chunk contains too little context to represent a complete idea , The individual chunks don't contain the complete rule.Important information split across chunks
  • Chunk too Large : A chunk contains too many unrelated concepts,contains lots of irrelevant information , Higher inference cost , More latency , Context-window pressure & Possible distraction of the LLM 
  • Overlap too large : The same content is repeated across many neighboring chunks, effectively retrieve one piece of information many times.
  • Overlap too small : Important information at a chunk boundary can be separated.


Chunking exists for three main reasons: embedding models have input limits, one vector must represent the entire chunk, and the LLM has a token budget. The second reason is the most important. If a chunk mixes several topics, its vector lands between them and matches none strongly, so large chunks cause retrieval misses. Small chunks match precisely but lose context: a sentence like 'this exception does not apply to corporate bookings' is useless without knowing which exception.

  • So chunk size trades match precision against answer completeness. 
  • Overlap protects facts that straddle boundaries: with overlap O, any span up to O+1 tokens is guaranteed intact in some chunk, at a storage cost of S over S minus O, which is why 10–20% overlap is a sensible default. 
  • Too much overlap multiplies cost and fills top-K with near-duplicates.


  • My default is structure-aware chunking: split on the document's own structure (headings, clauses, slides, functions), recursively split oversized sections, and prefix each chunk with its document title and heading path so it stands alone. 
  • For policy and manual content, I use parent-child: embed small children of around 200 tokens for precise matching, but return the parent section to the LLM. I choose per document type: clause-level for legal with cross-reference handling, one Q&A pair per chunk for FAQs, one product per chunk with structured attributes kept as filters for catalogs, AST-based for code, and tables with repeated headers, units, and periods for financial reports.
  • I never pick a size by convention. I run an experiment on a labeled eval set, compare configurations at an equal context-token budget rather than equal K, since bigger chunks otherwise get unfair extra context, and segment the results by query type. Semantic chunking is something I test against a recursive baseline rather than assume, since its gains are often inconsistent relative to its ingestion cost."



3. EMBEDDINGS : 


An embedding is a dense vector representation of text where geometric closeness approximates semantic relatedness. 

Mechanically, the text is tokenized, each token is looked up in an embedding matrix, a transformer encoder makes the token vectors context-aware, and pooling (mean, CLS, or last-token) produces one vector, usually L2-normalized.


Similarity Metrics :


Dot product: s = a · b                         range (−∞, ∞), sensitive to magnitude

Cosine: s = (a · b) / (‖a‖ ‖b‖)            range [−1, 1], angle only

Euclidean (L2):  s = ‖a − b‖ = √(Σ (aᵢ − bᵢ)²)     range [0, ∞), smaller = more similar



On normalized vectors, dot product, cosine, and Euclidean distance produce identical rankings. Dot product is the cheapest to compute, which is why systems normalize once at write time and then use inner product.



4 - Embedding :

  1. Simple: embeddings are coordinates on a map of meaning.
  2. Technical: a transformer encoder produces contextual token vectors, which are pooled and normalized into one vector, trained contrastively so related pairs are close.
  3. Production: a versioned embedding service guarantees identical treatment on both paths.
  4. Architecture: model choice is a long-term commitment, because switching means re-embedding the corpus, so I evaluate on my own data and plan blue/green migrations.

  • Closeness means something because the model is trained contrastively ,So similarity reflects what the training data paired together, not logical equivalence. That's why embeddings are weak at negation, exact IDs, and numbers, and why I pair them with BM25 and a reranker.
  • For metrics: on normalized vectors, cosine, dot product, and Euclidean give identical rankings, because squared L2 distance equals 2 minus 2 cosine. So I normalize at write time and use inner product. Absolute scores aren't portable across models because embedding spaces are anisotropic, so thresholds must be calibrated per model.
  • For model selection, I start from public leaderboards but decide on Recall@K on a golden set from my own corpus, then weigh input length, dimensions and storage (Matryoshka models allow truncation), latency, languages measured per language pair, data residency, and lock-in, since switching models means re-embedding everything. For jargon-heavy domains, I fine-tune with contrastive loss on query–passage pairs from logs or synthetic queries with hard negatives, or use a query-side adapter to avoid re-embedding.
  • The biggest production risk is mismatch: a different model, version, prefix, or preprocessing between ingestion and query produces garbage with no error. I prevent it with a single embedding service that owns all of that and stamps the model ID on every vector.



5 — VECTOR DATABASES

A vector index is an algorithm or data structure for nearest-neighbor search, found in libraries such as FAISS, hnswlib .


Index Types :

Flat Index : Stores raw vectors and scans all of them. There are no parameters, it is exact, and it is linear in cost. FAISS IndexFlatIP / IndexFlatL2 : Search time : O(N·d) per query.

HNSW (Hierarchical Navigable Small World) : graph-based Approximate Nearest Neighbor (ANN) : HNSW cuts search times down to (O(log N))

Think of it as a multi-level highway system for vectors.

Parameter

What it controls

Trade-off

M

The maximum number of bidirectional connection links each node can hold.

Higher M improves accuracy (recall) for complex high-dimensional data, but significantly increases index build time and RAM usage.

ef_construction

How many entry-point candidates are evaluated when inserting a new vector into the graph.

Higher values build a much higher-quality, better-connected graph, but dramatically slow down index creation times.

ef_search

How many nearest-neighbor candidates are tracked and evaluated during a live query.

Higher values increase your search accuracy (recall) but add slight latency to query response times.



IVF (Inverted File Index) : a highly popular approximate nearest neighbor (ANN) indexing mechanism used in vector databases to accelerate similarity searches across high-dimensional datasets. Instead of comparing a query vector to every single vector in the database (brute-force search), IVF partitions the vector space to drastically restrict the search scope, trading off a fraction of accuracy for massive gains in query speed

It has two main stages: training/indexing and querying.

  • Indexing Phase (Clustering) : 
  • Space Partitioning: The database uses an algorithm—typically k-means—to group the raw vectors into a specified number of geometric clusters (k, often configured as nlist). Each cluster is represented by a central point called a centroid. 
  • Inverted Mapping: The "inverted" concept borrows from classic text search, where a keyword maps to a list of matching document IDs. In vector IVF, the centroid identifier maps to a list of vectors (or their IDs) assigned to that specific cluster.


  • The Query Phase (Pruning) :
  • Step A (Centroid Search): When a new query vector arrives, the system calculates its distance against only the k cluster centroids to determine which clusters are geographically closest.
  • Step B (Partition Probing): Instead of scanning the entire database, the system isolates a user-defined number of the closest clusters (configured as nprobe) and performs a definitive search only within those subsets.


Parameter

What it governs

Performance Trade-off

nlist (or k)

Total number of clusters generated during training.

Higher nlist: Slower index creation/more centroid comparisons, but fewer vectors per cluster, resulting in faster query time.

nprobe

Total number of clusters actively searched during a query.

Higher nprobe: Scans more clusters, increasing accuracy/recall but increasing latency (approaching brute force if nprobe = nlist).

A tombstone in a vector database is a lightweight soft-delete marker that indicates a vector record has been deleted, without immediately removing its data or breaking the index.


The main index families: 

  • HNSW is a layered proximity graph with greedy descent and beam search at the bottom layer. Recall is tuned with M, ef_construction, and ef_search at query time. It's the low-latency default but memory-hungry and weak with deletes. 
  • IVF clusters vectors with k-means and scans only the nprobe nearest clusters, which is cheaper in memory and pairs well with product quantization. 
  • PQ splits vectors into sub-vectors and stores one-byte centroid codes, roughly 64× compression, using table-lookup distances. 
  • IVF-PQ with a full-precision refine step is the classic billion-scale recipe. 
  • In practice I often start with HNSW plus int8 quantization.



6 — RETRIEVAL


1. Dense Retrieval: This is bi-encoder retrival where queries and documents (actuall chunk vectors) are encoded independently into dense vector representations


Where dense retrieval fails:

  • exact identifiers ("BK-55120," "ERR_4012")
  • rare named entities
  • numbers and dates
  • negation
  • very short or very long queries
  • out-of-domain jargon


2. Sparse Retrieval ; Inverted Index


The analyzer pipeline runs identically on documents and queries: tokenize → lowercase → remove stopwords (optional) → stem or lemmatize → language-specific normalization. For Arabic, that means alef/yaa/taa-marbuta normalization and light stemming.


Types :


TF-IDF : A term matters if it is frequent in this document (TF) and rare across the corpus (IDF).

  • Term Frequency (TF): How often a query word appears in a document. If a word appears multiple times, the document is generally more relevant.
  • Inverse Document Frequency (IDF): How common a query word is across all documents. Rare words (like "BM25") carry significantly more weight than common words (like "the" or "system").
  • Document Length Normalization: How long the document is compared to the average document length in the database. A short document containing your keyword twice is usually more relevant than a 500-page book containing your keyword twice.

BM25: a highly efficient TF-IDF 


3. Hybrid Retrieval :  Dense + Sparse


Dense = semantic understanding

Sparse = exact lexical matching

Fusion Methods : 

Fusion = combining results from multiple retrieval methods into one final ranked list.

1. Score normalization + weighted sum  - Retrieve candidates using multiple methods → normalize their scores to a common scale → assign importance (weights) to each retriever → combine the scores → rank the documents again. This is commonly used in Hybrid RAG .

normalization type : 

  • min-max: (s − min) / (max − min) (per query, per retriever)  
  • z-score: s' = (s − μ) / σ
  • Softmax

weighting : The weights determine how much influence each retrieval strategy has. 


Ex : 

  • BM25 = 0.5 - Vector = 0.5 : Both are equally important.
  • BM25 = 0.3 - Vector = 0.7 : Semantic search is more important.


Scenario :

If an interviewer asks:

"Explain score normalization and weighted sum fusion in RAG."

A strong answer would be:

"Score normalization plus weighted sum is a hybrid retrieval fusion technique used to combine results from multiple retrievers such as BM25 and dense vector search. Since different retrievers produce scores on different scales, we first normalize their scores to a common range, such as 0 to 1. We then assign weights based on the relative importance of each retrieval strategy and calculate a combined score. For example, if BM25 has a normalized score of 0.8 and vector search has 0.9, with weights of 0.4 and 0.6, the final score is 0.4 × 0.8 + 0.6 × 0.9 = 0.86. We repeat this for all candidates, sort by the fused score, and pass the top candidates to an optional reranker and then the LLM. The key advantage is that keyword and semantic retrieval can complement each other, while the main challenge is choosing an appropriate normalization method and tuning the weights."


Problem: score distributions vary per query. One outlier BM25 score compresses all other normalized scores toward zero. α also needs tuning, and the best α may vary by query type.


2. Reciprocal Rank Fusion (RRF) : RRF does not care about the actual retrieval scores. It cares about the rank/position of a document in each retriever's result list.


Forget the scores. Use the rankings. Documents that consistently rank highly across multiple retrieval systems get rewarded.

Formula : 1/(k+rank).

Scenario :

Interviewer:

"You have BM25 and vector search. BM25 returns scores between 0 and 100, while vector search returns cosine similarity between 0 and 1. How would you combine them?"

Strong answer:

"I would consider Reciprocal Rank Fusion if I don't want to depend on score calibration. I would retrieve the top-K documents from both BM25 and vector search, assign each document a rank within each result set, and calculate an RRF score using 1/(k+rank).

.Documents that rank highly across both retrievers receive a higher fused score. This avoids the problem of comparing incompatible score scales. If I have reliable score normalization and need explicit control over the relative importance of each retriever, I could instead use normalized scores with a weighted sum. I would evaluate both approaches using metrics such as Recall@K, MRR, and NDCG."


4. Top-K and Retrieval Metrics : 


Top-K → How many retrieved documents/chunks do we keep  : Retrieval Metrics → How do we measure whether those retrieved documents are actually good .


Choosing K is a retrieval-quality vs context-noise trade-off.

Metrics : 


  • Recall@K -  measures what proportion of all the possible relevant items in the entire database were successfully captured within the top K results


Example: Suppose there are 20 total relevant documents for a query in your database. If your top 10 results (K = 10) contain 5 of them, your Recall@10 is 5/20 = (0.25) (or 25%). High recall means the system isn't missing important information


  • Precision@K : measures what percentage of the items in your top K results are actually relevant.


        Example  : If you ask a search engine for 10 results (K = 10) and 4 of them are useful, your Precision@10 is 4/10 = 0.40 (or 40%). High precision means fewer false alarms or junk results


Feature

Focus

Completeness / Coverage of all truth data



  • Hit Rate@K :  It answers a binary question: "Did the system find anything relevant at all within the top K results?"

For each query or user, the score is 1 (if at least one relevant result is in the top K) or 0 (if none are).

The final Hit Rate@K across a test set is the average of these 0s and 1s, represented as a value between 0.0 and 1.0.


Recall@K vs Hit Rate@K : Hit Rate only cares whether you found at least one relevant result & Recall cares how many relevant results you found.

  • MRR - Mean Reciprocal Rank : For a single query, you look at the position (rank) of the very first relevant result. You take the inverse (reciprocal) of that number: How high is the first good result? It cares only about how early the very first correct answer shows up.
    • If the first relevant result is at Position 1, the score is 1 / 1 = 1.0.
    • If it is at Position 2, the score is 1 / 2 = 0.5.
    • If it is at Position 4, the score is 1 / 4 = 0.25.
    • If no relevant result is retrieved, the score is 0.
  • NDCG@K (Normalized Discounted Cumulative Gain at rank K - Actual DCG divided by Ideal DCG (NDCG = DC / IDCG) 
    • This is one of the most powerful retrieval metrics because it considers:
    • Whether documents are relevant
    • How relevant they are
    • Where they appear in the ranking


A highly relevant document at rank 1 contributes more than the same document at rank 10.

Interview Answers : 


Retrieval has two complementary families. 

  • Dense retrieval uses a bi-encoder: queries and chunks are embedded independently and matched by ANN search. It handles paraphrase and cross-lingual matching, but struggles with exact IDs, rare entities, numbers, and negation. 
  • Sparse retrieval, typically BM25 over an inverted index, scores exact term overlap with IDF weighting so rare terms matter more, TF saturation so repetition has diminishing returns, and length normalization. It's excellent for codes and names but blind to synonyms.

Because they make different errors, I run both in parallel and fuse them. 

My default is Reciprocal Rank Fusion, one over 60 plus rank summed across retrievers, because it's rank-based, needs no score calibration, and rewards documents both retrievers agree on. 

Weighted normalized scores can do better when tuned on good eval data, but they're fragile to per-query score distributions. In practice, the reranker over the union of candidates often acts as the real fusion step.

I distinguish two Ks. K_retrieve, around 50, is optimized for recall and feeds the reranker; its cost is reranker compute. K_final, typically 3 to 10, goes into the prompt; its cost is LLM tokens, latency, and noise. I make K_final adaptive using reranker score thresholds and the token budget.

I measure Recall@K for the candidate stage, since that's the ceiling, NDCG and MRR for ranking quality, and Precision@K_final for context noise. Recall saturates as K grows while cost grows linearly, so I choose K from the knee of the recall curve on a golden set."



7 — QUERY TRANSFORMATION


IN RAG  - the process of using a Large Language Model (LLM) to modify, rephrase, or break down a user's raw input question before it is sent to a vector database or search engine

  • Query Rewriting - turns a query into a clear, standalone, retrieval-friendly form. This includes conversational condensation (resolving "it," "that one," "what about Abu Dhabi?"), spelling correction, and removing noise.
  • Query Expansion - adds synonyms, acronyms, and related terms, mostly to help BM25.
  • Query Decomposition - splits a complex question into independent sub-queries.
  • HyDE - the LLM writes a hypothetical answer passage, and you embed and search with that instead of the question. The intuition is that answer-to-answer similarity is higher than question-to-answer similarity.


Metadata Filtering

What it does: restricts search to relevant subsets (region, product, version, date, doc type). Filters can come from three sources:

  1. UI facets, which are the most reliable.
  2. The user profile (their region, their product tier).
  3. Extraction from the query.

Hard vs soft filters. A hard filter excludes non-matching documents. A soft filter boosts matching documents instead. Use hard filters for security and definite constraints ("version 4"), and soft boosts for uncertain extractions.


  • Interview :
  • Routing decides the backend. I cascade a cheap semantic router or classifier, escalating to an LLM only when confidence is low. Self-query converts language into schema-validated filters. The key safety rule is that LLM-generated filters can only narrow content, never touch security filters, with a fallback that relaxes content filters on zero results.


  • For latency, I combine rewriting, routing, decomposition, expansion, and filter extraction into one structured-output call with a small model, so the whole plan costs about 300 milliseconds.



9 — RE-RANKING


It is a second-pass evaluation step that re-orders an initial, broad set of retrieved documents so the most contextually relevant information sits at the very top before being fed to the Large Language Model


Retriever → find a reasonably large set of potentially relevant documents.

Reranker → carefully determine which of those candidates are actually most relevant to the query.



Cross-Encoder : The important thing is that the query and document can directly interact through Transformer self-attention at the token level.


Cross-Encoders generally provide better pairwise relevance modeling because query and document tokens interact through the Transformer's attention layers, allowing the model to capture fine-grained semantic relationships, terms, negations, and contextual dependencies. The trade-off is significantly higher inference cost because each query-document pair must be evaluated independently."



Interview :


  • Vector similarity alone isn't enough because bi-encoders compress the query and document independently into single vectors. There's no token-level interaction, so they capture topical similarity, not whether this passage answers this question, and they blur negation, numbers, and conditions. That's acceptable for the first stage, whose job is recall.
  • So I use two-stage retrieval: hybrid retrieval fetches around 50 candidates, then a cross-encoder reads each query–passage pair jointly, with full attention between them, and outputs a relevance score. Cross-encoders can't precompute anything, so they're only affordable on a shortlist. 
  • LLM rerankers, especially listwise, give the best quality and can follow instructions like 'prefer the current official policy,' but at roughly 15K input tokens and one to three seconds per query, I reserve them for a cascade on complex or high-value queries.
  • For options, managed APIs like Cohere Rerank give quality with zero ops but send data externally. Open-source rerankers like BGE's multilingual cross-encoder can be self-hosted on GPUs, which matters for data residency.

“Before choosing any technology, I’d spend the first few minutes on requirements, because in RAG they decide most of the architecture.

  • Evaluations : Finally, I’d agree acceptance gates up front: zero cross-permission leaks as a hard gate, recall and faithfulness thresholds per query category on a golden set, and a business KPI measured against a control group.
  • Only then would I sketch the architecture, and I’d tie every component back to one of these requirements.”

The business can’t give you labeled data. Now what?”

I hold short SME sessions where experts write gold answers for about 50 real questions. I add LLM-generated questions from the documents, reviewed by a human. Synthetic questions tend to share words with their source passages, which flatters lexical retrieval, so I weight real questions more. Then the set grows from production feedback, especially thumbs-down answers and escalations.

    • . Interview Answer (about 2.5 minutes)

I separate the system into four planes.

  • The offline indexing plane uses connectors driven by events plus periodic reconciliation, feeding a queue with retries and a dead-letter queue. A document registry tracks the version, content hash, and ACL hash of every document, so permission-only changes update metadata without re- embedding. Documents go through layout-aware parsing, with OCR only where scans matter, then cleaning and metadata extraction, including effective dates and status so superseded policies can be excluded. Then ACL mapping and PII handling, structure-aware chunking with parent links and page anchors, and embedding with the model version recorded on every vector. We write to a vector index, a BM25 index, and filterable metadata fields.
  • The online plane authenticates the user and resolves their groups into a permission filter, and if that fails, it fails closed. It rewrites follow-up questions and routes: documents go to RAG, numbers go to SQL or APIs, IDs go to exact lookups. Then it runs dense and sparse retrieval in parallel, with the permission filter inside each search, fuses the results with RRF, reranks about 50 candidates with a cross-encoder, and builds a deduplicated, budgeted context with citation IDs. The principle is recall early, precision late.
  • Generation uses a versioned prompt that separates trusted instructions from untrusted evidence, calls the LLM through a gateway with fallbacks, and validates citations before delivery. High-risk routes add claim-level verification.
  • Operations wrap all of it: per-stage traces, a golden set that gates CI, sampled online evaluation, index versions switched via aliases, and a degradation ladder down to search-only mode.
  • That is my baseline. Query expansion, compression, graph retrieval, and agentic loops come in only when evaluation shows a specific failure they fix.”

.  Follow Up Questions :


Your pipeline has a dozen stages. Why not just embed, take the top 5, and generate?”

That is my prototype, and it fails exactly where enterprises get hurt:

  • exact IDs (no sparse retrieval),
  • permissions (no ACL filter),
  • stale versions (no metadata),
  • ranking precision (no reranker),
  • debuggability (no traces).

Most of the added stages are offline and add no query latency. The online additions (parallel sparse retrieval, fusion, reranking) cost a few hundred milliseconds against an LLM that takes seconds. Each one stays only if the golden set shows it earns its place.

Where exactly do you enforce permissions? Why not filter right after retrieval, before the LLM?”

Inside the search, as a filter on principals in both the dense and sparse queries. Filtering after retrieval but before generation doesn’t leak if it’s implemented correctly, but it has two problems:

  • Recall collapses. If 45 of the top 50 results are forbidden, the user gets 5 weak candidates.
  • It’s fragile. Every code path, cache, and future feature must remember to apply the filter, and one omission is a leak.


The reranker adds about 250 ms. Justify it.

With evidence. I compare precision@5, NDCG, and end-to-end correctness on the golden set, with and without the reranker. In context, 250 ms is about 5% of a ~5-second request. A better ranking also lets me send fewer chunks, which cuts input tokens and partly pays for itself. If the evaluation shows no gain, I remove it. If it shows a gain but latency is tight, I reduce the candidate count, use a smaller reranker, or batch requests on GPU.


Answers are bad. Which component do you fix first?”

None, until I’ve localized the failure. I walk a failing sample through the trace, asking at each step:

  1. Is the answer in the corpus at all?
  2. Was it parsed correctly?
  3. Is it in the top 50 candidates?
  4. Is it in the reranked top 10?
  5. Did it make it into the final context?
  6. Was it used faithfully in the answer?

4. Chunking Strategy and Document Representation :


  • Chunking looks like a preprocessing detail. In practice it decides three things at once:
    • What can be found: the retrieval unit.
    • What the model reads: the generation unit.
    • What can be cited: the citation unit.



  • What a chunk is

A chunk is the unit that gets one embedding vector, one entry in the sparse index, a rank in retrieval, a slot in the context window, and a citation. Every downstream stage operates on chunks, so chunking errors spread through the whole pipeline.

  • Why chunk boundaries matter more than chunk size
    •             Most chunking failures come from where the cut falls, not how big the chunk is. Common examples:
    • a rule separated from its exception,
    • a table row separated from its header,
    • a list separated from the sentence that introduces it (“Exceptions:”),
    • a function cut in half.


  • Overlap costs you in two places:
    • At storage time: more vectors, more embedding cost, more index memory.
    • At retrieval time: adjacent overlapping chunks often get retrieved together. The same sentences then appear twice in the context and use up two of your top-K slots, which reduces the diversity of evidence.


  • How Chunk Size Affects Embedding Quality :
    • Large chunks dilute meaning
    • Tiny chunks lack meaning.
    • Hard limits truncate. Every embedding model has a maximum input length, and anything beyond it is dropped without warning.

Interview : 


I treat embedding selection as an evaluation problem, not a leaderboard lookup.

First, hard constraints filter candidates: data residency, license, required languages, and a max input length that covers my chunks. From the survivors, I shortlist three or four using public retrieval benchmarks in my languages. But I make the decision on my own golden set: real queries labeled at the span level, sliced by query type (policy questions, exact IDs, Arabic, jargon, OCR-noisy documents), searched against the full corpus with exact search, so I’m measuring the model and not ANN error. I report recall@50 and NDCG with confidence intervals, and I re-test the top two inside the real pipeline with BM25 and the reranker, because what matters is the marginal gain.


6: Vector Database and Index Selection : 


  • Exact vs. approximate
    • Exact k-nearest-neighbor (kNN) search compares the query with every vector. Cost grows linearly with N × d (number of vectors × dimension). Recall is perfect by definition.
    • ANN search organizes vectors so only a small fraction is examined, trading a little recall for large speed gains.


  • The index techniques :
    • Flat : Exact results , Trivial updates & Filtering is easy:
    • HNSW (Hierarchical Navigable Small World) : A multi-layer proximity graph , Upper layers are sparse, with long-range links; the bottom layer contains every vector, with local links. Very high recall at low latency, and good support for incremental inserts. Deletes are usually marked and cleaned up later during compaction or rebuild
    • IVF (inverted file index) : k-means clustering splits vectors into nlist clusters : A query probes the nprobe nearest clusters and scans only their members : Recall depends on nprobe.
    • Product quantization (PQ) : Each vector is split into m sub-vectors : IVF-PQ is the classic recipe for billion-scale search.
  • Index and System Decisions : 

HNSW ; M (how many contacts each person keeps per layer) , efConstruction (how many candidates a newcomer interviews before choosing their M contacts) & efSearch: how many leads you keep on your shortlist while searching.

  • Problem it solves: Real enterprise traffic mixes semantic questions with ID-bearing ones, and neither dense nor sparse retrieval covers both.
