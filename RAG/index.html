Retrieval-Augmented Generation

Look up evidence at answer time so the model reads the right text instead of relying only on its weights.

Retrieval-Augmented Generation (RAG) helps a large language model give better, more accurate answers by letting it look up information from external data sources before answering.

What is RAG

RAG, Retrieval-Augmented Generation, is a pattern where at inference time we retrieve evidence relevant to the user's question from an external knowledge store and inject it into the LLM's context, so the answer is grounded in, and attributable to, that evidence.

An LLM has two kinds of memory. Its weights are frozen at a training cutoff, lossy for long-tail facts, contain none of our private data, and can't enforce permissions. Its context window is precise but only lasts for one request. Models are much better at reading than remembering, so RAG's job is to find the right text and put it in front of the model.

That addresses four enterprise problems:

  • Freshness: updating knowledge means re-indexing a document, not retraining.
  • Private data: our documents stay in our store.
  • Attribution: every claim can cite a source.
  • Access control: we filter by the user's permissions at retrieval time, so the model only ever sees what that user is allowed to see.

RAG over a vector index is right for slowly to moderately changing unstructured knowledge. For real-time state, the retrieval step should be an API call.

How is RAG different from fine-tuning?

Fine-tuning means you retrain the model on new data so it “learns” that information permanently. You change the model itself by training it on new examples.

RAG means you do not retrain the model. You keep the model the same, but give it extra information at runtime — relevant information at the time of answering.

RAG focuses on knowledge access. Fine-tuning focuses on behavior and style.

Fine-tuning RAG
Expensive Faster to implement
Time-consuming Easier to update (just update the database)
Requires retraining No retraining required
Hard to update frequently More flexible
Information becomes part of the model Information stays outside the model
  • If the problem is about knowledge access → use RAG.
  • If the problem is about behavior change → use fine-tuning.

Prefer RAG when

  • Your data changes frequently
  • You need up-to-date information
  • You are using private or company documents
  • You want lower cost and faster implementation
  • You need traceable answers (with sources)

Examples:

  • Customer support chatbot using an internal knowledge base
  • Legal document assistant
  • Company HR policy bot
  • Medical research assistant

In all these cases, data updates often. Retraining every time would be expensive and slow.

Fine-tuning is better when

  • You want to change writing style or tone
  • You want domain-specific language behavior
  • You want the model to follow a strict format
  • You want behavior improvement, not just knowledge access

Why RAG exists: problems with a plain LLM

  • Knowledge cutoff. Weights are frozen at training time.
  • Hallucination. Generating fluent, plausible content that is unsupported or false.
  • Citation. You cannot cite weights. Banking, healthcare, legal, and insurance all require traceability: “show me where it says that.” RAG provides source IDs, page numbers, sections, and versions.
  • No access control in weights. A model cannot know that user A may see the M&A folder and user B may not. Anything in the weights is available to anyone who can prompt the model. RAG enforces authorization at retrieval time, so the LLM only ever sees documents the requesting user is allowed to see.

Context injection and grounded generation

Context injection means placing retrieved text into the prompt so it becomes part of the conditioning sequence.

Grounding is the property that every factual claim in the output is supported by the provided evidence. Injection is the mechanism; grounding is the contract. Injection alone does not guarantee grounding, because the model can still ignore, misread, or supplement the context.

A grounded setup has:

  • Evidence — relevant retrieved text
  • Instruction — “Answer only from sources; say if not found”
  • Attribution — cite source IDs per claim
  • Abstention — an explicit, acceptable “I don't know” path
  • Verification — post-generation check: claims ⊆ evidence

Faithfulness vs correctness

Faithfulness compares the answer with the context. Correctness compares it with the truth. A faithful answer built on an outdated source is still wrong.

Metadata

Chunking creates the searchable units. Metadata tells the retrieval system what those units are, where they came from, who can access them, and when they are valid.

Metadata is one of the things that makes retrieval accurate, secure, filterable, and maintainable.

Don't think of metadata as “extra information attached to a chunk.” Think of it as the control plane for your RAG system — it enables retrieval filtering, security, freshness, provenance, governance, and operational debugging.

Metadata enrichment

Make every chunk filterable, rankable, citable, and securable.

  • Source metadata: doc_id, title, URL, author, created_at / modified_at, source system
  • Structural metadata: heading_path (“Policy > Refunds > 7.2 Disruption”), page, chunk_index, parent_id
  • Security metadata: tenant_id, acl_groups, classification, data residency region
  • Lifecycle metadata: version, effective_from / effective_to, status (active / superseded / deleted)
  • Semantic metadata: language, doc_type, product, region, entities, keywords, summary, hypothetical questions

Common problems

  • Inconsistent tags (UAE vs AE vs United Arab Emirates) causing silent filter misses
  • Hallucinated LLM metadata
  • Stale ACLs

Chunking

Core concepts

  • Size
  • Overlap
  • Semantic boundaries. Natural units of meaning: sentence, paragraph, section, clause, function. Cutting between them preserves meaning; cutting through them destroys it.
  • Context preservation. Each chunk must be interpretable on its own.

Chunking strategies

  • Fixed-size + overlap
  • Sentence-based chunking
  • Paragraph-based chunking

Recursive chunking

Try the largest separator first (\n\n). If a resulting piece is still too big, split that piece with the next separator (\n, then ., then ,, and finally individual characters). Then greedily merge the small pieces back up to the size limit.

It prefers the most meaningful boundary available and only falls back to weaker boundaries when forced to.

Semantic chunking

Embed each sentence, measure the similarity between consecutive sentences, and cut where the topic jumps. The most common approach uses embedding distance thresholds: calculate the similarity between consecutive sentences and split the text when that similarity drops below a specific target.

Semantic chunking is a RAG preprocessing technique that uses semantic similarity between neighboring text segments to identify meaningful topic boundaries, producing coherent chunks that improve the quality of retrieval and downstream LLM responses.

Parent-child chunking (small-to-big)

Parent-child chunking is a RAG retrieval strategy where a document is divided into small child chunks for precise retrieval, while each child chunk belongs to a larger parent chunk that contains broader context.

This solves a common RAG problem: small chunks retrieve precisely but may lack context; large chunks provide context but can hurt retrieval precision.

Parent-child chunking separates retrieval granularity from generation context by indexing small child chunks for precise semantic search while using their larger parent chunks to provide sufficient context to the LLM.

Interview scenario

Question: You have a 500-page hotel policy document. Some policies are very detailed. How would you chunk it?

I wouldn't immediately choose a fixed token size. First I'd preserve the document hierarchy — document, section, subsection, and paragraph. I'd create parent chunks around coherent sections and then divide those parents into smaller child chunks based on semantic or structural boundaries. I'd embed the child chunks because they provide more precise retrieval representations, while maintaining a parent ID for each child. At query time, I'd retrieve the top-K child chunks, expand their parent IDs, deduplicate the parents, and optionally rerank the parent candidates. I'd then construct the final context within a token budget and send that to the LLM. Finally, I'd compare this against recursive or semantic chunking using retrieval and answer-quality metrics.

Proposition chunking

Proposition chunking (the “Dense X Retrieval” line of work) uses an LLM to rewrite text into atomic, self-contained factual statements (“The flight-disruption exception excludes corporate-account bookings.”). This gives very high precision, but ingestion is expensive.

Size and overlap failure modes

  • Chunk too small. The chunk contains too little context to represent a complete idea. The individual chunks don't contain the complete rule. Important information is split across chunks.
  • Chunk too large. A chunk contains too many unrelated concepts and lots of irrelevant information. Higher inference cost, more latency, context-window pressure, and possible distraction of the LLM.
  • Overlap too large. The same content is repeated across many neighboring chunks, so you effectively retrieve one piece of information many times.
  • Overlap too small. Important information at a chunk boundary can be separated.

Why chunking exists

Chunking exists for three main reasons: embedding models have input limits, one vector must represent the entire chunk, and the LLM has a token budget. The second reason is the most important. If a chunk mixes several topics, its vector lands between them and matches none strongly, so large chunks cause retrieval misses. Small chunks match precisely but lose context: a sentence like “this exception does not apply to corporate bookings” is useless without knowing which exception.

Chunk size trades match precision against answer completeness.

Overlap protects facts that straddle boundaries: with overlap O, any span up to O+1 tokens is guaranteed intact in some chunk, at a storage cost of S / (S − O). That is why 10–20% overlap is a sensible default. Too much overlap multiplies cost and fills top-K with near-duplicates.

A working default

The default is structure-aware chunking: split on the document's own structure (headings, clauses, slides, functions), recursively split oversized sections, and prefix each chunk with its document title and heading path so it stands alone.

For policy and manual content, use parent-child: embed small children of around 200 tokens for precise matching, but return the parent section to the LLM. Choose per document type:

  • Clause-level for legal, with cross-reference handling
  • One Q&A pair per chunk for FAQs
  • One product per chunk, with structured attributes kept as filters, for catalogs
  • AST-based for code
  • Tables with repeated headers, units, and periods for financial reports

Never pick a size by convention. Run an experiment on a labeled eval set, compare configurations at an equal context-token budget rather than equal K — bigger chunks otherwise get unfair extra context — and segment the results by query type. Test semantic chunking against a recursive baseline rather than assume it, since its gains are often inconsistent relative to its ingestion cost.

Embeddings

An embedding is a dense vector representation of text where geometric closeness approximates semantic relatedness.

Mechanically, the text is tokenized, each token is looked up in an embedding matrix, a transformer encoder makes the token vectors context-aware, and pooling (mean, CLS, or last-token) produces one vector, usually L2-normalized.

  • Simple: embeddings are coordinates on a map of meaning.
  • Technical: a transformer encoder produces contextual token vectors, which are pooled and normalized into one vector, trained contrastively so related pairs are close.
  • Production: a versioned embedding service guarantees identical treatment on both paths.
  • Architecture: model choice is a long-term commitment, because switching means re-embedding the corpus, so evaluate on your own data and plan blue/green migrations.

Similarity metrics

Metric Formula Range
Dot product s = a · b (−∞, ∞), sensitive to magnitude
Cosine s = (a · b) / (‖a‖ ‖b‖) [−1, 1], angle only
Euclidean (L2) s = ‖a − b‖ = √(Σ (aᵢ − bᵢ)²) [0, ∞), smaller = more similar

On normalized vectors, dot product, cosine, and Euclidean distance produce identical rankings, because squared L2 distance equals 2 − 2 · cosine. Dot product is the cheapest to compute, which is why systems normalize once at write time and then use inner product. Absolute scores are not portable across models because embedding spaces are anisotropic, so thresholds must be calibrated per model.

Closeness means something because the model is trained contrastively, so similarity reflects what the training data paired together, not logical equivalence. That is why embeddings are weak at negation, exact IDs, and numbers, and why they are paired with BM25 and a reranker.

Model selection

  • Quality: What is Recall@K on your golden set? Public leaderboards such as MTEB are a shortlist, not a decision. Domain shift and benchmark contamination make public scores unreliable for your corpus.
  • Max input length: Does it cover your chunk size without truncation?
  • Query latency: API round-trip vs self-hosted CPU or GPU inference.
  • Cost
  • Domain: legal, medical, code, finance — general vs specialized.
  • Dimensions and storage: Matryoshka models allow truncation.
  • Languages: measure quality per language pair.
  • Data residency and lock-in: switching models means re-embedding everything.

For jargon-heavy domains, fine-tune with contrastive loss on query–passage pairs from logs or synthetic queries with hard negatives, or use a query-side adapter to avoid re-embedding.

Embedding mismatch problems

The biggest production risk is mismatch: a different model, version, prefix, or preprocessing between ingestion and query produces garbage with no error.

  • Different model for query vs corpus
  • Silent version change
  • Missing or wrong prefixes

Prevent it with a single embedding service that owns all of that and stamps the model ID on every vector.

Vector databases

A vector index is an algorithm or data structure for nearest-neighbor search, found in libraries such as FAISS and hnswlib.

Flat index

Stores raw vectors and scans all of them. There are no parameters, it is exact, and it is linear in cost. FAISS IndexFlatIP / IndexFlatL2. Search time: O(N·d) per query.

HNSW (Hierarchical Navigable Small World)

Graph-based approximate nearest neighbor (ANN). HNSW cuts search time down to O(log N). Think of it as a multi-level highway system for vectors.

Parameter What it controls Trade-off
M The maximum number of bidirectional connection links each node can hold. Higher M improves accuracy (recall) for complex high-dimensional data, but significantly increases index build time and RAM usage.
ef_construction How many entry-point candidates are evaluated when inserting a new vector into the graph. Higher values build a much higher-quality, better-connected graph, but dramatically slow down index creation times.
ef_search How many nearest-neighbor candidates are tracked and evaluated during a live query. Higher values increase search accuracy (recall) but add slight latency to query response times.

Exact search vs approximate search

Exact k-nearest-neighbor (kNN) search compares the query with every vector. Cost grows linearly with N × d (number of vectors × dimension). Recall is perfect by definition.

ANN search organizes vectors so only a small fraction is examined, trading a little recall for large speed gains.

IVF (Inverted File Index)

IVF is an approximate nearest-neighbor index. Instead of comparing a query vector to every vector, it partitions the vector space and searches only part of it, trading a fraction of accuracy for much faster queries. It has two stages: training/indexing and querying.

Indexing (clustering). k-means groups the raw vectors into k clusters, often configured as nlist. Each cluster has a centroid. The centroid identifier maps to the list of vectors assigned to that cluster — the same idea as a keyword mapping to document IDs in classic text search.

Query (pruning).

  • Centroid search. Compare the query only to the cluster centroids and find the nearest clusters.
  • Partition probing. Search only inside the nprobe closest clusters.
Parameter What it governs Performance trade-off
nlist (or k) Total number of clusters generated during training. Higher nlist: slower index creation and more centroid comparisons, but fewer vectors per cluster, so queries are faster.
nprobe How many clusters are searched during a query. Higher nprobe: scans more clusters, raising recall, but latency rises and approaches brute force when nprobe = nlist.

Product quantization and scalar quantization

Product quantization (PQ) splits each vector into sub-vectors and stores one-byte centroid codes, roughly 64× compression, using table-lookup distances. IVF-PQ with a full-precision refine step is the classic billion-scale recipe. Each vector is split into m sub-vectors.

A practical starting point is HNSW plus int8 quantization.

Index families

  • Flat. Exact results, trivial updates, and easy filtering.
  • HNSW. A layered proximity graph with greedy descent and beam search at the bottom layer. Upper layers are sparse, with long-range links; the bottom layer contains every vector, with local links. Recall is tuned with M, ef_construction, and ef_search at query time. High recall at low latency, and incremental inserts work well. It is the low-latency default, but memory-hungry, and deletes are usually marked and cleaned up later during compaction or rebuild.
  • IVF. Clusters vectors with k-means and scans only the nprobe nearest clusters. Cheaper in memory, and pairs well with product quantization. Recall depends on nprobe.
  • PQ / IVF-PQ. Compression for billion-scale search, with a full-precision refine step.

HNSW parameters, when they are set

M is how many contacts each node keeps per layer. efConstruction is how many candidates a newcomer considers before choosing its M links. efSearch is how many leads stay on the shortlist while searching.

Tombstones

A tombstone in a vector database is a lightweight soft-delete marker that indicates a vector record has been deleted, without immediately removing its data or breaking the index.

Retrieval

Dense retrieval

Dense retrieval is bi-encoder retrieval: queries and documents (the chunk vectors) are encoded independently into dense vector representations.

Where dense retrieval fails:

  • Exact identifiers (BK-55120, ERR_4012)
  • Rare named entities
  • Numbers and dates
  • Negation
  • Very short or very long queries
  • Out-of-domain jargon

Sparse retrieval and the inverted index

The analyzer pipeline runs identically on documents and queries: tokenize → lowercase → remove stopwords (optional) → stem or lemmatize → language-specific normalization. For Arabic, that means alef / yaa / taa-marbuta normalization and light stemming.

TF-IDF. A term matters if it is frequent in this document (TF) and rare across the corpus (IDF).

  • Term frequency (TF): how often a query word appears in a document. If a word appears multiple times, the document is generally more relevant.
  • Inverse document frequency (IDF): how common a query word is across all documents. Rare words (like “BM25”) carry more weight than common words (like “the” or “system”).
  • Document length normalization: how long the document is compared with the average. A short document containing the keyword twice is usually more relevant than a 500-page book containing it twice.

BM25 is a highly efficient TF-IDF variant: IDF weighting so rare terms matter more, TF saturation so repetition has diminishing returns, and length normalization.

Hybrid retrieval

Dense retrieval is semantic understanding. Sparse retrieval is exact lexical matching. Run both in parallel, each with filters applied inside the search, fuse the ranked lists, and pass the fused candidates to the reranker.

Fusion combines results from multiple retrieval methods into one final ranked list.

Score normalization and weighted sum

Retrieve candidates with multiple methods, normalize their scores to a common scale, assign a weight to each retriever, combine the scores, and rank again.

  • Min-max: (s − min) / (max − min), per query and per retriever
  • Z-score: s' = (s − μ) / σ
  • Softmax

Example weights: BM25 0.5 and vector 0.5 means both are equally important. BM25 0.3 and vector 0.7 means semantic search matters more.

Score normalization plus weighted sum combines results from retrievers such as BM25 and dense vector search. Because they score on different scales, normalize first (for example to 0–1), then apply weights. If BM25 has a normalized score of 0.8 and vector search has 0.9, with weights 0.4 and 0.6, the fused score is 0.4 × 0.8 + 0.6 × 0.9 = 0.86. Sort by that score and pass the top candidates to an optional reranker, then the LLM. Keyword and semantic retrieval complement each other. The hard part is choosing the normalization and tuning the weights.

Score distributions vary per query. One outlier BM25 score compresses every other normalized score toward zero. The weight also needs tuning, and the best weight may vary by query type.

Reciprocal Rank Fusion (RRF)

RRF ignores the raw scores. It uses the rank of a document in each retriever's list. Documents that rank highly across systems get rewarded. The score for one list is 1 / (k + rank). A common default is 1 / (60 + rank), summed across retrievers.

If BM25 scores run from 0 to 100 and vector search returns cosine similarity from 0 to 1, use Reciprocal Rank Fusion when you do not want to depend on score calibration. Retrieve the top-K from both, assign each document a rank in each list, and score it with 1 / (k + rank). Documents that rank highly in both lists win. If scores can be normalized reliably and you need explicit control over each retriever, use a weighted sum instead. Compare both with Recall@K, MRR, and NDCG.

Weighted normalized scores can do better when tuned on good eval data, but they are fragile to per-query score distributions. In practice, the reranker over the union of candidates often acts as the real fusion step.

Top-K and retrieval metrics

Top-K is how many retrieved chunks you keep. Retrieval metrics measure whether those chunks are actually good. Choosing K is a retrieval-quality versus context-noise trade-off.

There are two Ks. K_retrieve, around 50, is optimized for recall and feeds the reranker; its cost is reranker compute. K_final, typically 3 to 10, goes into the prompt; its cost is LLM tokens, latency, and noise. Make K_final adaptive using reranker score thresholds and the token budget.

Measure Recall@K for the candidate stage, since that is the ceiling, NDCG and MRR for ranking quality, and Precision@K_final for context noise. Recall saturates as K grows while cost grows linearly, so choose K from the knee of the recall curve on a golden set.

Precision@K Recall@K
Focus Quality of the retrieved list Coverage of all relevant items
  • Recall@K. What proportion of all relevant items were captured in the top K. If 20 documents are relevant and 5 of them are in the top 10, Recall@10 is 5/20 = 0.25. High recall means the system is not missing important information.
  • Precision@K. What percentage of the top K items are relevant. If 4 of 10 results are useful, Precision@10 is 4/10 = 0.40. High precision means fewer junk results.
  • Hit Rate@K. A binary question: did the system find anything relevant in the top K? Each query scores 1 or 0. The reported hit rate is the average, between 0 and 1. Hit rate only cares whether you found at least one relevant result. Recall cares how many you found.
  • MRR (Mean Reciprocal Rank). For one query, take the rank of the first relevant result and invert it. Rank 1 scores 1.0, rank 2 scores 0.5, rank 4 scores 0.25, and no relevant result scores 0. It only cares how early the first correct answer appears.
  • NDCG@K. Normalized Discounted Cumulative Gain: actual DCG divided by ideal DCG (NDCG = DCG / IDCG). It considers whether documents are relevant, how relevant they are, and where they appear. A highly relevant document at rank 1 contributes more than the same document at rank 10.
Metric Main question
Recall@K Did I retrieve the relevant documents?
Precision@K How many retrieved documents are relevant?
Hit Rate@K Did I retrieve at least one relevant document?
MRR How high is the first relevant result?
NDCG@K Are highly relevant documents ranked near the top?

Interview answer

Retrieval has two complementary families. Dense retrieval uses a bi-encoder: queries and chunks are embedded independently and matched by ANN search. It handles paraphrase and cross-lingual matching, but struggles with exact IDs, rare entities, numbers, and negation. Sparse retrieval, typically BM25 over an inverted index, scores exact term overlap. It is excellent for codes and names but blind to synonyms. Because they make different errors, run both in parallel and fuse them. The default is Reciprocal Rank Fusion. Distinguish K_retrieve from K_final, and choose K from the knee of the recall curve on a golden set.

Query transformation

Query transformation uses an LLM to modify, rephrase, or break down a user's raw question before it is sent to a vector database or search engine.

  • Query rewriting turns a query into a clear, standalone, retrieval-friendly form. That includes conversational condensation (resolving “it,” “that one,” “what about Abu Dhabi?”), spelling correction, and removing noise.
  • Query expansion adds synonyms, acronyms, and related terms, mostly to help BM25.
  • Query decomposition splits a complex question into independent sub-queries.
  • HyDE has the LLM write a hypothetical answer passage, then you embed and search with that instead of the question. The intuition is that answer-to-answer similarity is higher than question-to-answer similarity.

Metadata filtering

Filters restrict search to relevant subsets: region, product, version, date, document type. They can come from three sources:

  • UI facets, which are the most reliable
  • The user profile (their region, their product tier)
  • Extraction from the query

A hard filter excludes non-matching documents. A soft filter boosts matching documents instead. Use hard filters for security and definite constraints (“version 4”), and soft boosts for uncertain extractions.

Routing decides the backend. Cascade a cheap semantic router or classifier, and escalate to an LLM only when confidence is low. Self-query converts language into schema-validated filters. LLM-generated filters can only narrow content. They never touch security filters. If content filters return zero results, relax them. For latency, combine rewriting, routing, decomposition, expansion, and filter extraction into one structured-output call with a small model, so the whole plan costs about 300 milliseconds.

Re-ranking

Re-ranking is a second pass that re-orders a broad set of retrieved documents so the most relevant information sits at the top before it is sent to the LLM.

  • Retriever: find a reasonably large set of potentially relevant documents.
  • Reranker: decide which of those candidates are actually most relevant to the query.

A cross-encoder lets the query and the document interact directly through transformer self-attention at the token level. That captures fine-grained relationships, terms, negations, and context better than a bi-encoder. The cost is higher, because each query–document pair is scored on its own. Cross-encoders cannot precompute anything, so they are only affordable on a shortlist.

Vector similarity alone is not enough. Bi-encoders compress the query and the document independently, so they capture topical similarity, not whether this passage answers this question, and they blur negation, numbers, and conditions. That is acceptable for the first stage, whose job is recall. Use two-stage retrieval: hybrid retrieval fetches around 50 candidates, then a cross-encoder scores each pair. LLM rerankers, especially listwise, give the best quality and can follow instructions such as “prefer the current official policy,” but at roughly 15K input tokens and one to three seconds per query, reserve them for a cascade on complex or high-value queries. Managed APIs such as Cohere Rerank need no operations but send data externally. Open-source rerankers such as BGE's multilingual cross-encoder can be self-hosted on GPUs, which matters for data residency.

RAG end-to-end design

Requirements

RAG is likely the backbone when the knowledge is too large for every prompt, it is private or changes often, different users may see different subsets, and answers need provenance. If three or more of these hold, start from RAG.

Before choosing technology, ask who will use the system, how many people, what it must withstand, the budget, and which constraints apply.

  • What decision or action does the user take after reading the answer?
  • What do they do today, how long does it take, and how often does it fail?
  • How will you decide whether this was worth building?

Is RAG appropriate?

  • How large is the corpus in tokens, and how fast is it growing?
  • How often does it change?
  • Does every user see the same content?
  • Must answers cite sources?
  • Are questions about text, numbers, or relationships between entities?

Personas, query types, sources, and expected answers.

  • Who are the top three user groups, and how do their needs differ?
  • Can you see search logs or ticket history?
  • Which system is authoritative when two sources disagree?
  • Can the best expert show what a perfect answer looks like?

Functional requirements define what the system does. Non-functional requirements define how well it does it. Ask stakeholders to rank quality, latency, and cost; what “fast enough” means and whether streaming is acceptable; and whether a stale answer is worse than no answer.

Estimate volume, growth, concurrency, QPS, latency, and tokens before choosing technology, so you know which constraint actually binds. A budget sketch keeps corpus size, index memory, traffic, and tokens in view. Example token mix: system prompt 800 + history 1,000 + evidence 4,500 + query 200 ≈ 6,500 input tokens, and about 400 output tokens. Index memory example: 6M vectors × 1,024 dimensions × 4 bytes (float32) ≈ 24.6 GB.

Security and regulatory constraints

The worst RAG incident is not a wrong answer. It is a correct answer given to the wrong person.

  • What classification scheme exists (public, internal, confidential, restricted)?
  • Must the index mirror source ACLs exactly? How are nested groups resolved?
  • Can data leave the region or go to a third-party LLM? Under what retention terms?
  • Are user queries logged, and for how long?
  • How are erasure requests handled?
  • Which regimes apply: GDPR, HIPAA, PCI DSS, national data-protection or localization laws, sector regulators? Who in legal or privacy signs off?

Infrastructure cost, sketched

  • Main LLM: $3.00 per 1M input tokens, $15.00 per 1M output tokens
  • Small LLM for query rewriting: $0.50 per 1M input tokens, $2.00 per 1M output tokens
  • Embeddings: $0.10 per 1M tokens
  • Self-hosted reranker: about $0.001 per query, amortized

Success criteria cover security, retrieval, generation, citations, latency, and cost.

Before choosing technology, spend the first minutes on requirements. Outcome: what does the user do with the answer, and what does a wrong answer cost? That sets how strict grounding and abstention must be. Taxonomy: real questions from logs or tickets. Aggregations belong in SQL, actions belong in tools, and navigational lookups might just need better search. RAG earns its place on synthesis across documents. The taxonomy also shows whether lexical retrieval is needed for IDs and error codes. Data: which systems are authoritative, how they change, their formats, and their permission models. The index is a second copy of the security model, so it must carry ACLs and stay in sync. Then measurable NFRs: p95 time to first token, a defined degraded mode, residency, a cost-per-query envelope, and two freshness SLOs. Content freshness is a quality issue; permission revocation is a security issue. For 20,000 employees, expect only a few QPS at peak, so throughput is not the binding constraint. LLM tokens per minute, the latency budget, and permissions are. Agree acceptance gates up front: zero cross-permission leaks as a hard gate, recall and faithfulness thresholds per query category, and a business KPI against a control group. Only then sketch the architecture, and tie every component back to one of these requirements.

If the business cannot give labeled data, hold short sessions where experts write gold answers for about 50 real questions. Add LLM-generated questions from the documents, reviewed by a human. Synthetic questions tend to share words with their source passages, which flatters lexical retrieval, so weight real questions more. Then grow the set from production feedback, especially thumbs-down answers and escalations.

The offline plane uses connectors driven by events plus periodic reconciliation, a queue with retries and a dead-letter queue, and a document registry that tracks version, content hash, and ACL hash, so permission-only changes update metadata without re-embedding. Documents go through layout-aware parsing, OCR only where scans matter, cleaning, metadata (including effective dates and status), ACL mapping, PII handling, structure-aware chunking with parent links and page anchors, and embedding with the model version on every vector. Write a vector index, a BM25 index, and filterable metadata. The online plane authenticates the user, resolves groups into a permission filter, and fails closed if that fails. It rewrites follow-ups and routes: documents to RAG, numbers to SQL or APIs, IDs to exact lookups. Dense and sparse retrieval run in parallel with the permission filter inside each search, results fuse with RRF, a cross-encoder reranks about 50 candidates, and the context is deduplicated and budgeted with citation IDs. Recall early, precision late. Generation uses a versioned prompt that separates trusted instructions from untrusted evidence, calls the LLM through a gateway with fallbacks, and validates citations. High-risk routes add claim-level verification. Operations wrap it: per-stage traces, a golden set that gates CI, sampled online evaluation, index versions switched via aliases, and a degradation ladder down to search-only mode. Query expansion, compression, graph retrieval, and agentic loops come in only when evaluation shows a specific failure they fix.

Follow-ups

Why not just embed, take the top 5, and generate? That prototype fails where enterprises get hurt: exact IDs (no sparse retrieval), permissions (no ACL filter), stale versions (no metadata), ranking precision (no reranker), and debuggability (no traces). Most added stages are offline and add no query latency. Parallel sparse retrieval, fusion, and reranking cost a few hundred milliseconds against an LLM that takes seconds. Each stage stays only if the golden set shows it earns its place.

Where do you enforce permissions? Inside the search, as a filter on principals in both the dense and sparse queries. Filtering after retrieval but before generation does not leak if it is implemented correctly, but recall collapses if 45 of the top 50 results are forbidden, and it is fragile: every code path, cache, and future feature must remember the filter.

The reranker adds about 250 ms. Justify it. Compare precision@5, NDCG, and end-to-end correctness on the golden set, with and without the reranker. 250 ms is about 5% of a ~5-second request. A better ranking also lets you send fewer chunks, which cuts input tokens. If evaluation shows no gain, remove it. If it helps but latency is tight, reduce the candidate count, use a smaller reranker, or batch on GPU.

Answers are bad. Which component do you fix first? None, until the failure is localized. Walk a failing sample through the trace:

  • Is the answer in the corpus at all?
  • Was it parsed correctly?
  • Is it in the top 50 candidates?
  • Is it in the reranked top 10?
  • Did it make it into the final context?
  • Was it used faithfully in the answer?

Document identity and versioning

Metadata extraction starts from source-system fields: ID, title, owner, created and modified dates, permissions, and sensitivity label.

What a chunk decides

Chunking decides three things at once: what can be found (the retrieval unit), what the model reads (the generation unit), and what can be cited (the citation unit).

A chunk is the unit that gets one embedding vector, one entry in the sparse index, a rank in retrieval, a slot in the context window, and a citation. Every downstream stage operates on chunks, so chunking errors spread through the whole pipeline.

Boundaries matter more than size. Typical failures: a rule separated from its exception, a table row separated from its header, a list separated from the sentence that introduces it (“Exceptions:”), a function cut in half.

Overlap costs you in two places. At storage time: more vectors, more embedding cost, more index memory. At retrieval time: adjacent overlapping chunks are often retrieved together, so the same sentences appear twice and use two top-K slots, which reduces the diversity of evidence.

Large chunks dilute meaning. Tiny chunks lack meaning. Every embedding model has a maximum input length, and anything beyond it is dropped without warning.

Embedding terms

Term Meaning
Dense vector A fixed-length list of real numbers, for example 1,024 dimensions, most of them non-zero
Dimension The length of the vector. It drives memory and search cost
Pooling How token vectors are combined into one text vector
Max sequence length Tokens beyond this limit are silently truncated
Asymmetric retrieval Short queries matched against longer passages, which often require role prefixes or instructions
Treat embedding selection as an evaluation problem, not a leaderboard lookup. Hard constraints filter candidates first: data residency, license, required languages, and a max input length that covers the chunks. Shortlist three or four using public retrieval benchmarks in those languages. Decide on your own golden set: real queries labeled at the span level, sliced by query type (policy questions, exact IDs, Arabic, jargon, OCR-noisy documents), searched against the full corpus with exact search, so you measure the model and not ANN error. Report recall@50 and NDCG with confidence intervals, and re-test the top two inside the real pipeline with BM25 and the reranker, because what matters is the marginal gain.

Retrieval strategy in the design

  • High recall at the candidate stage. Do not miss the evidence.
  • High precision at the final stage. Do not flood the context window.
  • Latency.
  • Cost.

Hybrid retrieval covers mixed traffic: semantic questions and ID-bearing ones. Run dense and sparse retrieval in parallel, each with filters inside the search, fuse the ranked lists, and pass the fused candidates to the reranker.
